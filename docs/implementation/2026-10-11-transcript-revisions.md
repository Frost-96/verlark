## 实施与边界

已有 #9 的确认文本追加、版本冲突检查和 #10 的反馈引用关系继续使用。本票补齐明确的公开有效性事实、版本关系的一致读取、中文指引与专项并发/浏览器证据。

- `Attempt.currentValidFeedback` 为当前确认文本对应的成功反馈，否则为 `null`。它由确认版本与反馈引用关系派生，不新增持久化布尔标记；失败、未知、处理中、无内容和旧版成功结果均不能代替当前有效反馈。零纠错项的成功反馈仍有效。
- 确认文本和反馈通过一次 SQL 左连接读取，使用同一个 PostgreSQL 语句快照；避免两个独立查询之间发生更正或反馈写回后拼接不同时间的关系。反馈按确认版本排序。
- `confirmTranscript` 继续在持有练习行锁的短事务内校验所有权、未结束状态、原始转写和预期确认版本，追加新版本。并发编辑仅一个成功，另一个返回 `stale`；不更新原始转写，不新增作答。
- 正在处理的 V1 反馈可以在 V2 确认后保存，但仅保留为 V1 历史反馈。V2 尚无结果时，V1 迟到不会恢复当前有效性；V2 已成功时，V1 迟到不会覆盖 V2 结果。
- 界面使用服务端导出的当前有效性，重新确认前提示会创建新版本，失效后提示为当前版本请求反馈，历史反馈明确写出“仅供对照，不适用于当前确认文本”，并保留对应版本和英语文本。
- 原有冲突恢复保留用户未保存的编辑；查询最新状态不静默换基准，用户明确“载入最新确认文本”后再核对确认。未确认编辑仍只保留在当前页面。

不需要新迁移：既有 `confirmed_attempt_revision_idx` 保证每次作答版本唯一，反馈确认 ID 主键与组合外键保证结果绑定确切的确认版本及作答。已从空库重新执行现有迁移验证。当前有效性是读取快照；后续结束操作仍必须在服务端写事务中按当时的版本关系和处理中请求重新判断，不能信任浏览器快照作为写入许可。

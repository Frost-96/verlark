# Verlark 重建执行计划

更新日期：2026-10-08。状态：基础阶段 #2–#6 已通过验收并经 PR #25 合入主分支，第二阶段从 #7 开始。依据：[架构设计](architecture-proposal.md)、[已确认范围](refactoring-design.md)、[领域词汇表](../GLOSSARY.md)。具体接入方案与部署可行性仍需按阶段验证。

用户故事、公开操作责任、可逐项验证的验收场景及延后事项见 [首版实施规格](first-release-spec.md)；本计划保留阶段顺序与实施安排。

## 交付目标

一个中文界面的英语听说学习网站，面向本人和测试名单中的少量用户。用户完成邮箱认证后，选择日常短对话，聆听并按需查看帮助，录下自己的表达，确认转写，获得中文表达反馈，再次作答或结束练习；之后可以查看、重练或删除练习记录。

技术栈为 Next.js、Drizzle、Neon、Better Auth，Vercel 优先。手机和电脑浏览器均在范围内。首版不包含双语切换、写作模块、独立 Coach、自由对话、自动复习计划、支付订阅或内容管理后台。

## 第一阶段：新骨架、数据与身份

目的：建立可以继续承载学习流程的真实应用基础，不先逐个迁移旧页面和旧表。

1. 保存实施前工作区的代码与文档快照，包含尚未提交的改动。确认快照可恢复；不使用 HEAD 替代当前工作区，也不把环境密钥、依赖缓存和构建产物纳入普通代码快照。
2. 读取当前安装版本的 Next.js 指南，核对 Drizzle、Better Auth 与驱动相容性，锁定稳定版本和可复现依赖。
3. 建立 `identity`、`learning-content`、`practice` 三个业务 Module、中文页面骨架、配置校验及类型、格式、lint 和测试命令。按架构设计组织 `server.ts` 与可供浏览器引用的 `contracts.ts`，集中装配依赖；跨 Module 不导入内部查询，外部 Adapter 不写业务状态。清理与当前替换范围直接相关的旧入口和依赖，避免新旧认证同时决定身份。
4. 建立认证表、材料版本、表达任务、练习、作答、确认文本版本、反馈与技术处理记录所需的新模型及 SQL 迁移。表定义归所属 Module，数据库目录汇总迁移所需定义；不建立通用 Repository。反馈引用确切确认文本版本，技术处理状态与练习状态分开。具体字段以实现审查为准，不复刻旧写作/口语表。
5. 集成 Better Auth，完成测试名单检查、邮箱注册登录、验证、密码恢复、退出和会话撤销。先以明确的开发邮件替身验证应用行为，保留真实邮件接入点。
6. 在独立空测试数据库验证迁移和身份流程；不默认将现有 DATABASE_URL 指向的数据库当作可清空测试环境。若无可用测试库，报告未验证项，不能把生成迁移 SQL 等同于迁移运行成功。

阶段验收：可复现安装、类型检查、lint 和生产构建通过；空库迁移通过；非测试名单注册被拒绝；验证与密码恢复令牌行为符合设计；退出或撤销的会话不能继续操作业务；所有权检查覆盖跨账号读写。邮件替身验证不代表真实投递已成功。

## 第二阶段：一份材料贯穿完整学习流程

1. 提供一份经过检查的日常短对话、可播放的开发素材、原文、中文释义、提示和表达自身情况的任务。材料源文件随项目维护，发布到持久化内容版本；验证部署包不再包含旧源文件时，历史内容仍可读取。音频保留规则仍留待存储决策。
2. 实现材料选择、聆听、录音、识别结果核对、反馈、重录、结束、历史和删除。测试替身明确可见，并仅在开发/测试配置启用。
3. 保留各次作答；反馈绑定确认文本版本；历史练习固定材料版本。重录、重新识别与重新请求反馈分别处理，不能都表示为新作答。
   已结束练习不再追加作答，重练创建新练习；中途退出保留未结束练习供继续或删除。表达反馈允许零个纠错项，不能为满足数量强制挑错。
   作答以主动提交并成功接收为起点，未提交录音不进入历史。未结束时更正确认文本需保留旧反馈并重新请求新反馈，结束后内容只读；至少一次作答有当前有效反馈且无正在处理的请求即可结束，其他作答保留真实状态。
   历史重练引用原内容版本，材料目录开始引用最新版；验证发布新版不改变历史，旧版撤下后禁止用该版重练并明确提示，不自动替换。
4. 通过 `practice` 公开 Interface 实现开始、重练、提交、确认、反馈、重试、结束、读取与删除；再次作答复用新提交。界面可读取允许动作和失败原因，但服务端每次写入重新检查所有权、状态与版本。浏览器仅持有录音草稿、播放、提示和未确认编辑等临时状态。
5. 实现稳定提交标识、数据库唯一约束、并发结果检查与失败恢复。相同标识重发返回同一接收结果，不同内容复用同一标识返回冲突。短事务登记处理权，事务外调用 Adapter，再以短事务检查处理权、目标版本和记录状态后写回。结束、提交和发起处理共享并发控制；处理权有期限与明确恢复路径，失效请求不得写回，不将本地失效解释成远端已取消。
6. 通过 Module Interface 编写行为测试，使用隔离的真实 PostgreSQL 与外部 Adapter 替身，不断言内部调用次数。检查反馈结构及中文说明、零至两个问题和英文引用等质量样例；不把结构校验或固定替身输出当作模型质量证明。

阶段验收：用户可以走完流程并看到历史；重复提交不生成重复作答，识别重试不增加作答次数；识别和反馈失败可恢复；修改确认文本后旧反馈不能冒充当前反馈或单独满足结束条件；一次作答有效、另一次失败时仍可按规则结束；并发结束与提交不破坏只读规则；超时恢复后旧请求不得写回；修改材料不改变历史，撤下旧版阻止原版重练；删除后旧请求不能把记录复活。上述验收使用替身时只证明业务流程，不代表学习效果或真实服务质量。

## 第三阶段：真实接入与部署验证

1. 按用户已允许延后的范围，集中比较并确定识别、反馈生成、材料音频、邮件、文件存储及预算。录音保留期限和删除规则与存储一同定案。
2. 用实际服务替换测试接入，检验供应商协议、超时、取消、重复请求及费用控制，不将测试用固定反馈带入真实体验。
3. 验证 Vercel 的打包、请求大小、执行时长和数据库连接；依据实际媒体流程判断是否需要 FFmpeg，不机械继承旧实现。
4. 完成中国大陆和海外访问、手机和电脑浏览器麦克风录音、实际识别、反馈、邮件和历史回放验证。部署地区根据实测选择。

阶段验收：至少一条使用真实服务的完整学习流程通过；邮件可实际收取；私有录音访问与删除符合最终规则；开发替身不能在正式环境被误启用。未完成这些验收不能宣布首版可用。

## 第四阶段：内容扩充与首版试用

扩充到已确定的日常交流主题，检查材料文本、音频、提示和任务的一致性。通过用户实际试用调整难度，观察用户是否能表达自己的情况及利用反馈再次尝试，不用“完成次数”冒充能力提升。

清理已确认废弃且不再被新功能调用的旧代码、翻译配置、Prisma/Supabase 接入和依赖。保留适用的 QA 行为证据与新测试，不保留废弃功能只是为了维持旧测试数量。

## 实施边界

- 架构设计已于 2026-10-08 获用户确认，当前实施阶段为第二阶段，按每阶段的可验证结果推进；不重复询问已确认的设计，也不需要每修改一个文件再次询问。实施状态以 GitHub Issues 与 docs/implementation/ 中的证据为准。
- 服务供应商、音频存储、保留规则、预算和部署地区仍按已约定的接入阶段决定，不在骨架实现中暗中选定。
- 放弃旧数据兼容不等于删除现有远端数据库或文件；本计划不包含对旧云端资源的销毁。
- 类型、构建、自动测试、浏览器操作和真实供应商测试分别报告结果；没有执行的检查不标记通过。
